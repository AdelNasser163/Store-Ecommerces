## One migration entry point and execution order

The future entry point is `supabase/setup.sql`, generated by
`node tools/build-supabase-setup.cjs`. It wraps the following in **one transaction**:

1. `supabase/preflight.sql`: PostgreSQL version, expected column types, primary
   keys, foreign keys, existing managed-table policies/triggers and settings keys.
2. `202611220001_existing_model.sql`: base schema, canonical policies, authoritative
   checkout, compatibility support view and role helpers.
3. `202611220002_relations_and_queries.sql`: normalized relations and queries.
4. `202611220003_overview.sql`: dashboard aggregates.
5. `202611220004_safe_operations.sql`: bounded status updates/search.
6. `202611220005_customer_privacy.sql`: sanitized customer order RPC.
7. `202611220006_security_review.sql`: final grants, order guards, reservation
   lifecycle, payment settlement restrictions and unified support authorization.

Do not run selected fragments or stop between files on a live database. Some
earlier definitions are superseded by the final migration in the same transaction.
The complete setup is designed to be repeatable; runtime repeatability of this
reviewed revision has **not** been executed. Source grammar checks alone do not
prove idempotence. Legacy `support-setup.sql` now deliberately refuses execution.
`db/admin-schema.sql` is a legacy test fixture, not the production entry point.

## Preservation and compatibility

- Existing products, customers, orders and support-message records are not deleted,
  replaced, truncated or seeded by setup. Product JSON is no longer updated just
  to backfill images. Missing derived image rows are inserted without replacing
  existing ones. Existing non-null order/customer associations stay unchanged.
- Missing optional support fields/relations are added. Existing null order/customer
  associations can be linked to matching existing customer records.
- Profiles/default settings are inserted only when missing. Existing values stay.
- Legacy `support_private.admins` rows are retained but confer no authorization.
  They are never automatically promoted into store-wide administrator roles.
- Known project-owned policies and triggers are reinstalled. Unknown managed-table
  policies/triggers, unexpected column types/keys/relationships and unknown settings
  keys cause an exception instead of being removed or guessed. Unrelated Storage
  object policies also require review before proceeding.
- Incompatible custom schemas, extra required columns, custom checks, data that
  violates new constraints, or conflicting objects can abort the transaction.
  Existing constraints/indexes are not dropped to force success. Review these on a
  staging copy; a source-only review cannot certify unseen production metadata.
- A failed complete transaction rolls back its schema/data changes. Take a verified
  database backup first anyway; do not use table deletion as a rollback procedure.

## Required manual Supabase steps, after staging validation

1. Back up the existing database and verify restoration into a separate staging
   project/copy. Review migration exceptions there before any production attempt.
2. Use a trusted SQL Editor/project-owner account for schema installation. The
   browser publishable key cannot perform migrations. Never put service-role keys,
   database passwords or provider secrets in frontend files.
3. Review the `product-images` bucket: it is intended for **public product assets**,
   WebP uploads only, at most 12 MB. Existing bucket settings are not overwritten.
   Private documents/customer attachments must not be placed in this public bucket.
4. Ensure the `supabase_realtime` publication exists and Realtime is enabled.
   Setup registers the explicit project tables; it does not publish every table.
5. Configure Auth Site URL and allow the exact storefront `auth.html`,
   `reset-password.html` and `admin-login.html` callbacks, plus intentional local
   development URLs. Configure confirmation/reset email delivery. Google OAuth
   additionally needs an actual configured Google provider.
6. Create the first administrator as described below. Review any former support
   administrators individually and assign `staff` or `admin` deliberately.
7. Test public/customer/staff/admin access using **different real Auth accounts**,
   including role escalation attempts, customer isolation and two-device Realtime.
   Test parallel checkout, duplicate retries, double cancellation and stock limits.
8. Import existing browser-local real business data only via a reviewed import;
   this migration does not automatically upload localStorage/demo data.
9. Keep `supabase-config.js` set to `enabled:false` until the unfinished integration
   items below are resolved. Then rebuild with `npm run build:performance` and test
   a staging deployment before publishing production bundles.

### Exact first-administrator initialization

In the **existing** Supabase project, open **Authentication → Users → Add user**
and create/invite the intended administrator. Verify the email, then copy that
Auth user's UUID. Do not create a second project or infer admin authority from
user-editable metadata or an email address sent by the browser.

After schema installation and staging approval, the trusted operator's SQL is:

```sql
do $$
declare admin_id uuid := 'REPLACE_WITH_AUTH_USER_UUID'::uuid;
begin
  if not exists (
    select 1 from auth.users
    where id = admin_id and email_confirmed_at is not null
  ) then
    raise exception 'Create and verify this Auth user first';
  end if;
  insert into public.user_roles(user_id, role)
  values (admin_id, 'admin')
  on conflict (user_id) do update set role = excluded.role;
end $$;

select user_id, role
from public.user_roles
where user_id = 'REPLACE_WITH_AUTH_USER_UUID'::uuid;
```

Use `admin-login.html` with that Auth account. New registration creates a profile,
never an administrative role. A trusted operator can assign `staff` instead of
`admin` through the same reviewed role table. No public role-grant RPC exists.

## Permission contract

| Identity | Permitted operations |
| --- | --- |
| Anonymous | Published catalog/public settings, public product assets, validated/throttled support submission, authoritative COD checkout. No private inbox/customer/order reads. |
| Customer | Same public operations; own profile/contact data and sanitized own-order history; own linked support threads/replies. No roles/settings/inventory writes. |
| Staff | Read operational dashboard/catalog/customers/inbox; edit catalog/bundles/customer contact fields; manage messages/replies; update order status and internal notes within server guards; upload/update product images. No role assignments, settings writes, commercial order rewrites, verified-payment writes or destructive catalog/image deletes. |
| Admin | Staff operations plus role/settings management and permitted catalog/image deletion. Still cannot confirm online payment or rewrite immutable commercial order fields from the browser. |
| Trusted server | Payment transaction/provider-event operations and settlement RPC. Provider authenticity must be checked by server webhook code first. |

## Inventory and payment behavior

- New authoritative checkout deducts stock transactionally and records product,
  variant and bundle-component reservations. Payment rows are created for these
  orders. Frontend-supplied totals, stock markers or payment-confirmed fields are
  not accepted as authority. Raw authenticated order INSERT is revoked.
- A permitted pre-shipment, unpaid cancellation restores each recorded reservation
  once and marks it released in the same transaction. Repeating cancellation cannot
  restore twice. Cancelled/completed orders cannot be reopened.
- Shipped or verified-paid orders need an explicit return/refund workflow and are
  not silently restocked. Reserved variants cannot be removed while outstanding.
- Historical orders have no inferred reservations: their actual stock history is
  unknown. Cancelling them does **not** invent stock restoration. Reconcile them
  manually using real records before adopting a different rule.
- The service-only settlement RPC checks event identity, provider reference, amount
  and currency. Failed/cancelled unsettled payments cancel eligible orders and use
  the same reservation release path. A late successful settlement after stock was
  released flags reconciliation instead of falsely confirming/fulfilling the order.
- **Online card/ValU checkout is deliberately refused by the cloud RPC.** There is
  no deployed/verified provider webhook in this repository. A frontend confirmation
  must never enable it. The service-only SQL RPC is not itself a provider webhook.

## Unresolved features and production gates

- Real payment provider selection, server payment creation, signed raw-body webhook
  verification, provider-side amount/status lookup, refunds and automatic reservation
  expiry/scheduling. There is no simulated payment success or browser fallback.
- Hosted migrations, runtime RLS/grant tests, actual login/confirmation/recovery,
  Storage upload/delete and cross-device Realtime tests.
- Outbound support email delivery (saving a reply is not sending email).
- Remaining broader backend work: fully paginated/scoped storefront catalog bridge,
  bundle selection/metrics, complete asset lifecycle and shipping-provider integration.
- Public form abuse protection beyond per-email/per-phone database throttling;
  server-verified CAPTCHA is needed if distributed abuse occurs.
- Actual production catalog/constraint/index inspection and staging restoration test.
